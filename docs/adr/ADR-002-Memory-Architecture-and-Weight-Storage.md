# ADR-002: Memory Architecture and Weight Storage

## Status
Accepted

## Context
The audio thread must not perform any heap allocations or deallocations during real-time processing.
All working memory for the SSM inference must be pre-allocated. The weights for the Mamba-SSM model
must be stored in a way that is efficient for real-time reading and does not incur runtime overhead.

## Decision
### Memory Pre-allocation
- All inference working memory (state vectors, temporary buffers, etc.) is pre-allocated during the
  `activate()` call. The maximum block size is known from the host (or we use a fixed maximum block
  size, e.g., 512 samples, and allocate accordingly).
- We allocate:
  - The state vector `h_state` of size `state_dim` (for each layer, if multi-layer).
  - Temporary buffers for the SSM computation (e.g., for the convolution and the state update).
  - Any other buffers needed for the inference (e.g., for the input and output of the block).

### Weight Storage
- The weights are stored in a memory-mapped read-only file. This allows the operating system to
  handle paging and caching efficiently, and we avoid copying the weights into writable memory.
- The weight file is cache-aligned (typically 64-byte alignment) to ensure efficient loading.
- The weight file format is flat binary, with a header that includes metadata (state dimension, number
  of layers, etc.) and then the weights for each layer in a predetermined order.

### Compile-Time Model Dimensions
- The maximum model dimensions (state dimension, number of layers, etc.) are fixed at compile time
  via a `config.h` header generated by the ML export tool. This allows us to allocate arrays with
  known sizes and avoid dynamic allocation.
- If we wish to use a different model (e.g., a 50M-param model instead of a 1M-param model), we
  regenerate `config.h` with the new dimensions and recompile. The weight file must also be
  regenerated to match the new dimensions.

## Consequences
- The audio thread has deterministic memory access and no allocations.
- Weight loading is done once (during initialization) via memory mapping, so there is no cost during
  real-time processing.
- The system is flexible to different model sizes by changing the compile-time configuration and
  the weight file.

## Implementation Notes
- We use `mmap` (or equivalent on Windows) to map the weight file into memory. The memory mapping
  is read-only.
- The weight file must be structured so that we can cast a pointer to the header and then to the
  weights for each layer without any pointer chasing or indirection that would cause cache misses.
- We define a struct for the weight file header that includes:
  - Magic number and version
  - State dimension (`state_dim`)
  - Number of layers (`num_layers`)
  - Any other model-specific dimensions (e.g., expansion factor, convolution kernel size)
  - The total size of the weight data (for validation)
- The weights for each layer follow the header in a predetermined order (e.g., for each layer: the
  weights for the input projection, the convolution, the state update, and the output projection).
